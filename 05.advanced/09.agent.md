The dxflow agent turns a natural-language request into a runnable workflow and then operates it. It never runs containers itself — it drives the same workflow engine described in [Core Concepts](/docs/advanced/concepts), taking one step at a time based on where the work stands.

::callout{color="blue"}
The agent is an interface *over* the engine, not a separate runtime. Everything it does maps to a workflow API call you could make yourself — see the [CLI](/docs/cli/agent) and [API](/docs/api/agent) references.
::

## Providers

The agent is model-agnostic. It selects a provider from the configured `agent-url`, so the same engine can run against Claude, Gemini, or any OpenAI-compatible endpoint.

| `agent-url` contains | Provider |
|----------------------|----------|
| `anthropic.com` | Claude |
| `googleapis.com` | Gemini |
| anything else | OpenAI-compatible |

Configure it in a profile or via environment variables:

```bash
dxflow config set agent-url https://api.anthropic.com
dxflow config set agent-key sk-ant-...
dxflow config set agent-model claude-sonnet-5
```

::callout{color="amber"}
`agent-key` must be set or prompting fails. `agent-model` is the default for every turn and can be overridden per prompt with `--model` (CLI) or the `model` body field (API).
::

## Phases

A session's phase is derived from the bound workflow's live status on every turn — you never set it by hand.

::card-group
  ::card{title="Design" icon="i-hugeicons:pencil-edit-02"}
  No workflow bound yet. Turn the request into one workflow definition and create it.
  ::

  ::card{title="Deploy" icon="i-hugeicons:rocket-01"}
  A workflow is bound. Start and stop it, and watch logs and stats while it runs.
  ::

  ::card{title="Debug" icon="i-hugeicons:bug-01"}
  A step exited non-zero. Read logs, inspect files, stage a fix, and re-run.
  ::
::

| Phase | When | What you can do |
|-------|------|-----------------|
| **design** | no workflow bound | search templates, compose a workflow, create it |
| **deploy** | a workflow is bound and running or ready | start, stop, and watch logs and stats |
| **debug** | the bound workflow exited with a failed step | read logs, inspect files, upload a fix, re-run |

Each phase only offers the actions that make sense for it — so you can't, for example, stop a workflow that isn't running.

## Working with the agent

You interact by prompting in plain language. Each prompt is one turn: the agent replies with a short message and takes the next step for the current phase — searching, composing, starting, reading logs, and so on. Its actions and their results are recorded in the session, so the next prompt builds on them.

```bash
dxflow agent ask <identity> "compose an ubuntu desktop with fastqc"
dxflow agent ask <identity> "start"
dxflow agent ask <identity> "show me the logs"
```

::callout{color="blue"}
Work one step at a time. The agent decides its next action from the request and the current state, then reports back — prompt again to continue.
::

## Observing a run

While a workflow is deployed, you can ask the agent for its progress — steps, events, logs, and stats — at any time, including mid-run. The agent presents these as a compact, readable view rather than the raw engine output, so what you see is tuned for quick understanding. The [API reference](/docs/api/agent) documents the dedicated endpoints for each if you're integrating programmatically.

## Sessions

A session is created against a workflow identity (or none, for design) and persists its history, token usage, and phase snapshot on the engine. Prompting advances it one turn; listing, inspecting, and removing sessions work like any other engine resource.

```bash
dxflow agent create --workflow ebc954e7f50e
dxflow agent ask <identity> "start"
dxflow agent history <identity>
```

See the [CLI reference](/docs/cli/agent) for every command and the [API reference](/docs/api/agent) for every endpoint.
